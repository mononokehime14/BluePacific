# 03 · Roofline 与 Memory-bound 算子

> 学习目标：拿到任何一个 op（或一整层、一整个模型），能在 30 秒内算清它的字节数、判断它卡在带宽还是算力、说出优化上限是多少倍，并且**用自己的机器测出证据**。
>
> 这份笔记里的所有数字，都是在本机（i7-14650HX / Windows）上用 `tools/bench_roofline.py` 实测的，你可以重跑复现。

---

## 0. 一句话结论

**所有推理优化最终只做两件事：减少搬运的字节数（融合、量化、复用、换布局），或者提高算力利用率（tiling、向量化、tensor core）。判据就是 `AI = FLOPs / Bytes` 和硬件的 `ridge = 峰值算力 / 峰值带宽` 的比值 —— 而实际系统里 90% 的 op 位于斜线（带宽墙）那一侧。**

---

## 1. 为什么这是量化和 kernel 的公共地基

同一个 roofline，能回答三个方向的问题：

| 问题 | 用 roofline 怎么答 |
|---|---|
| **这个 op 该优化什么？** | 算 AI，比 ridge。低于 ridge → 优化字节数；高于 ridge → 优化 MAC 利用率。优化错方向 = 白干。 |
| **量化能带来多少加速？** | 量化只减字节、不减 FLOPs。所以加速上限 = 原字节数/新字节数，**且仅在 memory-bound 时成立**。 |
| **我的 kernel 写得好不好？** | 达到的 GB/s ÷ 峰值 GB/s。memory-bound 的 op 达不到 60~80% 就是没写好，别再调别的了。 |

面试里这三个问题几乎是必问的，而且**答错方向比答不上来更糟** —— 比如面试官问「decode 怎么加速」，你答「上 tensor core」，基本就结束了。

## 2. Roofline 的三个公式

### 2.1 定义

```
AI    = FLOPs / Bytes                    （算术强度，单位 FLOP/Byte）
Peak  = 峰值算力 (FLOP/s)
BW    = 峰值带宽 (Byte/s)
ridge = Peak / BW                         （拐点，单位 FLOP/Byte）

可达性能 = min(Peak, AI × BW)
```

### 2.2 那张图

```
 性能
 (FLOP/s)
   │                        ┌───────────────  Peak（算力墙）
   │                       /
   │                     /   ← 拐点处 AI = ridge
   │                   /
   │                 /       斜线：AI × BW（带宽墙）
   │               /
   │             /
   │___________/________________________________ AI (FLOP/Byte)
         memory-bound  │  compute-bound
```

- 斜线左边：`AI < ridge`，性能 = AI × BW，**再怎么加算力也没用**。
- 斜线右边：`AI > ridge`，性能 = Peak，**再省带宽也没用**。
- 拐点：`AI = ridge`，两条墙一样高。**这是唯一值得记住的数**。

> 单位提醒：note 01 用的是 MAC/Byte，本文用 FLOP/Byte。`1 MAC = 2 FLOP`，换算除以 2。厂商的 TOPS 直接当 FLOP/s 用（int8 的 ops）。

### 2.3 不同硬件的 ridge（约数，用来建立数量级直觉）

| 硬件 | 峰值算力 | 峰值带宽 | ridge (FLOP/B) | 意味着 |
|---|---|---|---|---|
| 本机 i7-14650HX (fp32, 实测) | 929 GFLOPS | 34.5 GB/s | **27** | 笔记本 CPU 的拐点很低，大部分 op 都是带宽墙 |
| Apple M2 (fp32) | 3.6 TFLOPS | 100 GB/s | 36 | |
| RTX 4090 (fp32) | 82.6 TFLOPS | 1008 GB/s | 82 | |
| A100 80G (fp16 TC) | 312 TFLOPS | 2039 GB/s | 153 | |
| H100 SXM (fp16 TC) | 989 TFLOPS | 3350 GB/s | 295 | |
| **手机 NPU (int8, 45 TOPS)** | 45 TOPS | ~68 GB/s | **~660** | 拐点高 20 倍 → 端侧几乎一切都是带宽墙 |

**这张表最该记住的一行是最后一行**：手机的 int8 ridge ≈ 660，而 MobileNetV2 的 depthwise 只有 4.5 FLOP/Byte（fp16 口径；fp32 下是 2.2，即 note 01 里的 ≈1.1 MAC/Byte）。**差了 150 倍** —— 这就是「NPU 标称 45 TOPS，实测跑不满 5%」的数学解释。

## 3. 第一步永远是数字节：R/W 记账法

**大部分人是死在这一步的**：只数了输入输出，忘了中间临时张量。数错字节 → AI 错 → 方向错。

规则：给每个 op 标 `R`（读一次全量）和 `W`（写一次全量），字节数 = `(R+W) × N × sizeof(dtype)`。

| op | 朴素实现 | 融合后 | 字节缩减 |
|---|---|---|---|
| `y = x + 1` | 1R+1W | — | — |
| `y = relu(conv(x))` | conv: 1R(w)+1R(x)+1W；relu: 1R+1W → **2R+2W** | **1R+1W** | 2× |
| `y = silu(gate(x)) * up(x)`（SwiGLU） | gate: 1R+1W；up: 1R+1W；mul+silu: 2R+1W → **4R+3W** | **2R+1W** | 2.3× |
| RMSNorm（朴素） | `x*x` 1R+1W（临时数组）；`mean` 1R；缩放 1R+1W → **4R+2W** | **2R+1W** | 2× |
| softmax（朴素） | max 1R；sub 1R+1W；exp 1R+1W；sum 1R；div 1R+1W → **5R+3W** | **1R+1W**（online） | 4× |
| GEMM `[M,K]@[K,N]` | `M·K + K·N + M·N` | 同 | — |

两个容易漏的：
- **广播**：`x + bias` 里 bias 只读一次（小），别按全量算。
- **量化后的 dtype**：W4 时权重字节是 fp32 的 1/8，但**激活通常还是 fp16** —— 算字节时要分别算。

## 4. 本机实测：把 roofline 画出来

### 4.1 峰值

| 指标 | 实测值 | 怎么测的 |
|---|---|---|
| 峰值带宽（4 线程 copy） | **34.5 GB/s** | 2×128MB 数组对拷，`copy = 1R+1W` |
| 峰值带宽（单线程 copy） | 27.3 GB/s | 同上，单线程 |
| 纯读带宽（BLAS dot） | 33.8 GB/s | 只读，不写 |
| 峰值 fp32 算力 | **929 GFLOPS** | `4096×4096 @ 4096×512`，OpenBLAS |
| **ridge point** | **27 FLOP/Byte**（13.5 MAC/B） | 929 / 34.5 |

对照：i7-14650HX 是 8P+8E，笔记本上通常是 DDR5-5600 双通道（理论 89.6 GB/s；若是 4800 则 76.8）。**实测只有 34.5 GB/s，是理论值的 38%** —— 这不是测量错误，是笔记本内存子系统的常态（单/少核很难打满双通道）。**面试时说「实测 35 GB/s，理论 90」比背 spec 值可信得多。**

### 4.2 各 op 的达成率

| op | ms | GB/s | %bw | GFLOPS | AI (FLOP/B) | 判定 |
|---|---|---|---|---|---|---|
| copy (1R+1W) | 7.79 | 34.46 | 100% | 0 | 0.00 | 带宽墙 |
| add (2R+1W) | 17.04 | 23.63 | 69% | 1.97 | 0.08 | 带宽墙 |
| silu (1R+1W) | 72.55 | 3.70 | **11%** | 1.85 | 0.50 | 带宽墙（实际是 SFU 墙） |
| rmsnorm 朴素 (4R+2W) | 109.39 | 14.72 | 43% | 1.23 | 0.08 | 带宽墙 |
| rmsnorm einsum (2R+1W) | 42.17 | 19.10 | 55% | 3.18 | 0.17 | 带宽墙 |
| softmax 朴素 (5R+3W) | 63.96 | 16.79 | 49% | 2.62 | 0.16 | 带宽墙 |
| gemv 8192×4096 | 2.93 | 45.78 | 133% | 22.88 | 0.50 | 带宽墙 |

**四个可以当场讲的观察：**

1. **所有 op 的 `%flop` 都 < 3%** —— 一台声称 929 GFLOPS 的机器，跑这些 op 时算力单元基本在睡觉。这就是 memory-bound 的体感。
2. **rmsnorm 朴素 → einsum：109ms → 42ms，2.6×**。唯一改动是**省掉一个 `x*x` 的临时数组**（256MB 的全量读写）。这是「字节数决定一切」最干净的证据，比任何理论都好讲。
3. **silu 只有 11% 带宽**：因为 `exp` 是超越函数，CPU 上每个元素要十几个 cycle，瓶颈从内存变成了 SFU。**推论：elementwise 不一定都是带宽墙**，具体要看它的每字节运算量。在 GPU/NPU 上 SFU 快得多，才退化成带宽墙。
4. **gemv 达到 133%** —— 超过 copy 的「峰值」。这不是测错：copy 有写分配（write-allocate）的额外流量，纯读 kernel 的可用带宽就是更高。**所以「峰值带宽」不是一个数，是一族数**；roofline 只能是数量级判断，不能当精确预言。

### 4.3 用 batch 扫描把拐点测出来

固定 `M=K=4096`，扫 batch N（GEMM 的 AI 随 N 线性增长）：

| N | ms | GFLOPS | GB/s | AI | 占峰值 |
|---|---|---|---|---|---|
| 1 | 1.40 | 24 | 48.0 | 0.5 | 3% |
| 4 | 2.00 | 67 | 33.6 | 2.0 | 7% |
| 16 | 2.45 | 219 | 27.7 | 7.9 | 24% |
| 32 | 2.77 | 388 | 24.6 | 15.8 | 42% |
| 64 | 3.29 | 652 | 21.0 | 31.0 | **70%** |
| 128 | 5.19 | 827 | 13.7 | 60.2 | 89% |
| 512 | 18.49 | **929** | 4.5 | 205 | 100% |
| 2048 | 80.13 | 858 | 1.7 | 512 | 92% |

```
GFLOPS
  929 ┤                                                    █   N=512
  870 ┤                                              ▉         N=256
  827 ┤                                        ▉               N=128
  652 ┤                              ▊                         N=64
  388 ┤                    ▌                                   N=32
  219 ┤            ▍                                           N=16
   67 ┤      ▎                                                 N=4
   24 ┤  ▏                                                     N=1
      └──┬────┬────┬────┬────┬────┬────┬────┬────┬──
        N=1   4   16   32   64  128  256  512
        ←───── 带宽墙 ─────→↑←──── 算力墙 ────→

```

**实测拐点（N≈32~64）和理论 ridge（27）对上了。** 这件事的意义：**你可以不查任何 spec，只用一条扫描曲线就测出自己机器的 ridge**。面试时这么讲，比背「H100 是 295 FLOP/Byte」强十倍。

## 5. 六类 memory-bound 算子的解剖

### 5.1 Elementwise（add / mul / silu / 残差）

- 字节：`(2R+1W)` 起步（两输入一输出）。
- 优化：**只有融合一条路**。省一次读写就接近 2×，没有别的技巧。
- 判断要不要融合：算「省下的字节 ÷ 带宽」和「一次 kernel launch 的开销」哪个大。
  - decode（batch=1）：hidden 4096 fp16 = 8 KB，省一次读写 ≈ 0.5 µs < launch 开销 → **不值得单独融合**（但顺手融进 GEMM 的 epilogue 是免费的）。
  - prefill（batch=4096）：4096×4096 fp16 = 32 MB，省一次读写 ≈ 1 ms → **必须融合**。

> 记住这个不对称：**融合是为 prefill 服务的，decode 的瓶颈在权重和 KV。**

### 5.2 RMSNorm / LayerNorm

- 朴素：`x*x` → 临时数组（这是最大的一笔浪费），总计 **4R+2W**。
- 两遍：算 `mean(x²)`（1R），再缩放（1R+1W）= 3 遍。
- 一遍：把整行留在寄存器 / shared / VTCM 里，边读边累加平方和，读完直接用缓存的行做缩放 → **2R+1W**（行放得下才行，`hidden=4096` fp16 是 8 KB，放得下）。
- LayerNorm 比 RMSNorm 多一个 pass（要减均值再算方差；用 `E[x²]-E[x]²` 一次算完会有数值稳定性问题）。**这就是 Qwen3.5 全用 RMSNorm 的原因之一**（另一个原因是精度，见 note 02）。
- 理论上限：`4R+2W → 2R+1W` 是 **2×**；实测 **2.6×**（多出来的是临时数组的分配与 page fault）。**实测收益 > 理论收益在 memory-bound 里很常见**，因为 allocator 的时间也进了计时器。

### 5.3 Softmax

- 朴素 5R+3W。
- online softmax：一遍流式算 max 和 sum，第二遍归一化 → 2R+1W。
- FlashAttention 干的事：**把 softmax 和 `PV` 矩阵乘融合，让 `S` 根本不出片上内存**。省的不只是 softmax 的 5R+3W，更是整个 `L×L` 注意力矩阵的落盘（`L=4096`、fp16、单 head 就是 32 MB）。
- 严格说它**不减少 FLOPs**（复杂度不变），而是把**内存复杂度从 O(L²) 降到 O(L)**。这是「融合把瓶颈从带宽侧挪走」的最强案例，面试必答。

### 5.4 GEMV / decode 的 Linear

- 字节：`M·K·sizeof(w)`，**权重只读一次，与 batch 无关**。
- 所以 decode 的耗时 ≈ 全部权重的字节数 ÷ 带宽，**与算力无关**。
- 直接推论：
  ```
  token/s 上限 ≈ 带宽 / 模型字节数
  9B 模型 @ 4bit = 4.5 GB；手机 68 GB/s → 66 ms/token → 15 tok/s
  9B 模型 @ 8bit = 9 GB；  手机 68 GB/s → 132 ms/token → 7.5 tok/s
  ```
  **这就是「为什么端侧一定要做 weight-only 量化」的全部理由**，一行公式讲完。
- 实测印证：本机 gemv 8192×4096 用时 2.93 ms，读 128 MB → 45.8 GB/s，已经贴着纯读带宽了。**说明 BLAS 的 GEMV 没什么可优化的了，想更快只能减字节。**

### 5.5 Attention decode（KV 读取）

- 每生成 1 个 token，要把**所有历史 K、V** 读一遍：`2 × n_kv × head_dim × L × bytes`。
- Qwen3.5-9B 级配置（note 02）：每 token 每层 2048 元素 × 8 个 full attention 层 = 16384 元素。

| 上下文 | KV 大小 (fp16) | 读一遍 @68 GB/s | 占 66ms 权重时间的比例 |
|---|---|---|---|
| 4k | 134 MB | 2.0 ms | 3% |
| 32k | 1.07 GB | 16 ms | 24% |
| 128k | 4.3 GB | 63 ms | 95% |

**结论：短上下文时 KV 可以忽略，长上下文时 KV 会反超权重。** 这就是 GQA / MLA / 线性注意力 / KV 量化存在的全部动机，也是 Qwen3.5 只给 1/4 的层留 KV 的原因。

### 5.6 Depthwise Conv

- 字节：`N·H·W·C × (1R+1W)`，FLOPs = `9 × N·H·W·C` → AI = 18 FLOP / (2×2 bytes) = **4.5 FLOP/B**（fp16）。
- 离本机 ridge 27 差 6 倍，离手机 NPU 的 660 差 146 倍。**它永远是带宽墙，任何「提升 MAC 利用率」的努力都是错的。**
- 优化只有三条：① 去掉 im2col（note 01 讲过，9× 膨胀）；② 滑窗复用（相邻输出共享 2/3 的输入）；③ channel-last 让 C 方向能向量化。

## 6. 用 roofline 做决策（三个真实场景）

### 6.1 量化什么时候才有加速？

因为**量化只减字节、不减 FLOPs**：

```
加速比 ≈ min(1, 字节_old/字节_new)     仅当 memory-bound
加速比 ≈ 1（甚至 <1，因为要 unpack）    当 compute-bound
```

于是有一个**批大小阈值**（对 `[M,K]@[K,N]`，权重主导时 `AI ≈ 2N / sizeof(w)`，单位 FLOP/Byte）：

| 权重精度 | `AI ≈` | 转 compute-bound 的 batch | 含义 |
|---|---|---|---|
| fp16 | `N` | **N ≈ 27**（本机 ridge） | batch > 27 后量化不再提速 |
| int8 | `2N` | **N ≈ 14** | |
| int4 | `4N` | **N ≈ 7** | 量化让「拐点左移」，模型更早变成 compute-bound |

**这句话值一个 offer**：
> 「W4 相对 fp16 在 decode（batch=1）能拿到接近 4× 的带宽收益，在 prefill（batch=512，AI≈460）几乎拿不到收益，甚至因为 unpack 更慢。所以端侧量化的收益全在 decode 上，prefill 要靠 int8 的 tensor core 或者干脆不量化。」

### 6.2 Prefill vs Decode：把 Qwen3.5 的一层算一遍

MLP（`4096 → 12288 → 4096`，权重 50.3M 参数/矩阵 × 3 = 151M 参数）：

| 场景 | 权重字节 (fp16) | 激活字节 | FLOPs | AI | 判定 | 时间由谁决定 |
|---|---|---|---|---|---|---|
| Decode，1 token | 302 MB | 16 KB | 302 M | **≈1** | 带宽墙 | 302 MB / 34.5 GB/s ≈ **8.8 ms** |
| Prefill，512 token | 302 MB | 34 MB | 154 G | **≈460** | 算力墙 | 154 G / 929 GFLOPS ≈ **166 ms** |

**同一层，两个场景的 AI 差 460 倍，时间由两面完全不同的墙决定。**

注意一个陷阱：prefill 时权重仍占总字节的 **90%**，但它早就不是瓶颈了。**「谁占字节多」和「谁是瓶颈」是两件事** —— 这正是必须用 AI 而不是字节占比做判断的原因。面试里能把这一点讲清楚，说明你真的懂 roofline，而不是背了个公式。

于是两个阶段的优化方向彻底分开：

- decode 优化 = 减字节（量化、KV 压缩、投机解码）；
- prefill 优化 = 提高算力利用率（tiling、tensor core、int8 GEMM）；
- 两者**没有任何一个技巧是通用的**。

### 6.3 该不该写融合 kernel？先算收益上限

```
收益上限 = 省下的字节 / 峰值带宽
```

- 省 32 MB @ 34.5 GB/s = 0.93 ms。如果这个 op 现在只占 1.2 ms，那融合最多值 4×；如果它占 0.1 ms，融合毫无意义。
- **先 profile 拿到每个 op 的耗时占比，再决定写不写 kernel。** 面试官问「你怎么优化一个模型」，第一句应该是「先 profile」，不是「先融合」。

## 7. 把同一套方法搬到 NPU / 手机上

| roofline 概念 | 在 HTP / QAIRT 上的对应物 |
|---|---|
| 峰值带宽 | DDR 带宽（LPDDR5X ~68 GB/s），但**真正决定性能的是 DDR↔VTCM 的搬运量** |
| 峰值算力 | int8 MAC array 的 TOPS（注意是 int8，fp16 通常减半或更低） |
| ridge | int8 下 ≈ 660 FLOP/B → **绝大多数 op 都是带宽墙** |
| bytes 记账 | profile 里看每个 op 的 DDR read/write 字节数，和理论值对 |
| L2/L3 cache | VTCM（容量小、必须自己 tiling）+ 系统 cache |
| 融合 | NPU 的 op fusion 通常在离线编译期做（QNN 的 graph 优化），运行时改不了 |

**实践建议**：在手机上做 roofline，先看 profile 里的 **DMA 时间占比**。如果一个 op 的 execute 时间远小于 DMA 时间，那它是带宽墙，去优化 kernel 的 MAC 利用率是浪费时间 —— 应该去改 tiling、改 layout、或者往上游改量化方案。

> 工具名以你手上的 SDK 版本为准（QNN / QAIRT 的 profiler 会给 per-op 的执行时间与内存流量）。

## 8. 面试问答（10 题）

**Q1：什么是 roofline？ridge point 怎么算？**
性能上限 = min(峰值算力, AI×带宽)，AI = FLOPs/字节。两条墙的交点就是 ridge = 峰值算力/带宽。AI 低于它 → 带宽墙，优化字节数；高于它 → 算力墙，优化 MAC 利用率。**关键是这个判据能在动代码之前就告诉你方向对不对。**

**Q2：给你一个 op，怎么判断它卡在哪？**
三步：① 数字节（R/W 逐次记，别漏临时张量）；② 算 FLOPs 和 AI；③ 和硬件的 ridge 比。想更严谨就实测：跑一次，看达到的 GB/s 是不是贴着峰值 —— 贴着就是带宽墙。

**Q3：为什么 decode 是 memory-bound？给数字。**
batch=1 时每个权重只用一次，AI ≈ 1~2 FLOP/Byte，远低于任何现代硬件的 ridge（本机 27，手机 660）。时间 ≈ 模型字节数 / 带宽。9B@4bit = 4.5 GB，68 GB/s → 66 ms/token ≈ 15 tok/s。**算力完全没用上。**

**Q4：prefill 为什么相反？**
batch=N 时权重被复用 N 次，AI ≈ N（fp16）。N=512 时 AI≈460，远超 ridge，变成算力墙。所以 prefill 的优化是 GEMM 效率（tiling、tensor core），decode 的优化是字节数。**两个阶段要用两套优化。**

**Q5：RMSNorm 为什么比 LayerNorm 快？**
少一个 pass：RMSNorm 不减均值，只需 `mean(x²)`；LayerNorm 要算均值和方差。而且用 `E[x²]-E[x]²` 一次算完会有数值稳定性问题（大数相消），实际实现往往还是两遍。**在带宽墙上，少一遍就是快一倍。**

**Q6：softmax 为什么要融合？FlashAttention 省了什么？**
朴素 softmax 是 5R+3W。更关键的是注意力矩阵 `L×L` 必须落盘再读回；FlashAttention 用 online softmax 把 `QKᵀ → softmax → PV` 融成一个 tile 内的循环，`S` 从不出片上内存 —— 省的是 **O(L²) 的落盘**。注意它不减少 FLOPs，改变的是内存复杂度（O(L²) → O(L)）。

**Q7：量化为什么在 decode 有效、在 prefill 无效？**
量化只减字节不减 FLOPs。decode 是带宽墙，减 4× 字节 ≈ 4× 加速；prefill 是算力墙（AI≈460），此时瓶颈是 MAC 利用率，减权重字节换不来时间，反而多了解包开销。**所以「W4 一定比 W8 快」是错的，取决于 batch。**

**Q8：你的 kernel 达到 60% 带宽，算好吗？**
对 bandwidth-bound 的 op，60~80% 是正常水平，80%+ 很好了。判断方法：和同访问模式的 kernel 比（纯读 vs 读写混合的峰值不一样，我实测 copy 34.5 而 gemv 45.8 GB/s）。**先确认天花板在哪，再评价自己。**

**Q9：为什么 MobileNet 在 NPU 上算力利用率很低？**
它的 depthwise 层 AI ≈ 4.5 FLOP/Byte，而手机 NPU 的 int8 ridge ≈ 660 —— 差 150 倍。整个网络在 batch=1 时 AI 只有个位数，永远是带宽墙。**所以「TOPS 翻倍」对它几乎无效，端侧优化的第一优先级是减少搬运。**

**Q10：roofline 的局限是什么？**
① 不建模延迟和并行度（一个 op 的 32 个 warp 只跑起来 4 个，roofline 看不出来）；② 不建模 cache 层次，用 DRAM 带宽算会把「其实命中 L2」的 op 判错；③ 假设访存和计算能完全重叠；④ 对融合后的复合 op，AI 要重新算。**说得出局限，比只会套公式高一档。**

## 9. 动手实验（每个 30~60 分钟，做完就能讲）

- [ ] **实验 1：跑出自己的 roofline。** 运行 `python tools/bench_roofline.py`，把结果表替换成本机数字。验收：能解释每一个 `%bw` 为什么是那个值（尤其是 silu 的 11% 和 gemv 的 133%）。
- [ ] **实验 2：把 rmsnorm 再压一遍。** 目前朴素 → einsum 是 2.6×。试着用 `numexpr` 或写一个「单遍 + 手写平方和」的版本，看能不能逼近 `2R+1W` 的理论上限（42ms → ？）。验收：给出「实测 / 理论上限」的比值。
- [ ] **实验 3：测自己机器的拐点。** 用 GEMM 扫描，画出 GFLOPS vs N 曲线，找到拐点，和 `peak_flops/peak_bw` 比。验收：两个数差在 2× 以内，并能解释为什么不是完全相等。
- [ ] **实验 4：验证量化阈值。** 把 GEMM 的权重换成 int8（unpack 后做 fp32 乘），再扫一遍 batch。验收：曲线拐点左移，且 batch=1 时明显更快、batch≥128 时更慢。**这一个实验就能把「量化只在 decode 有用」从我说的变成你自己测的。**
- [ ] **实验 5（有设备再做）：手机上对一遍。** 拿一个 QNN/QAIRT 的 profile，找一个 op，用它的 DDR 字节数算 AI，看和 profile 里的 DMA 时间占比是否一致。
